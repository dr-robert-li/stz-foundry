## Findings

**1. §7 — "one row past that table's own ceiling" is arithmetically wrong.**
- **Claim:** The pinned `PAIRED_CRITICAL_VALUE_TABLE` covers `[20, 60]`, and "this suite's 75 pairs land one row past that table's own ceiling."
- **Attack:** 75 − 60 = 15. The suite's maximum discordant count lands *fifteen* rows past the ceiling, not one. This matters beyond pedantry: "one row past" suggests the existing table nearly suffices and lulls a reader into thinking the gap is marginal; a 15-row gap (20% of the suite's range) is a substantial uncovered region where `evaluatePairedGate` would throw on 15 distinct possible outcomes.
- **What would have to change:** Correct the sentence to state the actual gap (15 rows, n_d 61–75 uncovered), or delete the characterization and just state the covered range and the suite's range.

**2. §8 — The stated reason for rejecting truncated per-role inputs is arithmetically incoherent with the section's own output truncation.**
- **Claim:** Feeding the outer hash truncated 16-hex (64-bit) per-role digests "would narrow the outer hash's own effective collision resistance to that 64-bit surface, a needless weakening" — while two paragraphs later the outer hash's *output* is itself "truncated to the same 16-hex-character width" (64 bits).
- **Attack:** The final `definitionHash` is 64 bits wide either way, so the construction's effective collision resistance is ~2^32 work (birthday bound over a 64-bit id space) regardless of whether the inner digests were truncated. The "needless weakening" the section rejects is exactly the weakening it accepts one paragraph later at the output stage. The rejection rationale as written is false; the actual security level is set by the output truncation, which the section does not acknowledge as the binding constraint.
- **What would have to change:** Either (a) state honestly that the id space is 64-bit by house convention and that inner-truncation is rejected only on marginal/structural grounds, not collision-resistance grounds, or (b) widen the output if 64-bit collision resistance is actually the concern the rejection paragraph claims it is.

**3. §8 — `componentVariantId` cannot both be "unchanged" and "produce the 32-byte digests the outer hash consumes."**
- **Claim:** "`componentVariantId` itself is unchanged, still called once per role to produce each of the two 32-byte digests the outer hash consumes."
- **Attack:** The section's own citation (`src/harness.ts:370-372`, `createHash("sha256").update(definitionText).digest("hex").slice(0, 16)`) shows `componentVariantId` returns a 16-hex-character truncated string — not a full 32-byte digest. If it is truly called unchanged to feed the outer hash, the outer hash consumes truncated 64-bit values — the exact construction this section claims to reject in finding 2. If instead a new full-digest function feeds the outer hash, then the claim "called once per role to produce the 32-byte digests" is false. The section asserts both horns.
- **What would have to change:** Name the actual full-digest producer (a new helper, or `createHash` inline) and correct the sentence so `componentVariantId` is described as producing only the 16-hex diagnostic per-role hashes, with the 32-byte digests coming from a distinct, named code path.

**4. §5 — Cross-reference to the candidate hash points at the wrong section.**
- **Claim:** The task record carries "the builder/answerer prompt pair (for the CD-04 hash, §9)."
- **Attack:** The CD-04 hash is specified in §8; §9 is module filenames. In a document whose entire premise is that reviewers can walk claims to their evidence without paraphrase, a wrong internal pointer in the freeze-governed text is exactly the class of defect the freeze protocol exists to catch.
- **What would have to change:** Change "§9" to "§8".

**5. §3 — The contract's own TOCTOU defense contains a residual TOCTOU, and the failure-mode list omits the recorded-hash-side failures.**
- **Claim:** "The re-hash at read time is exactly the check that catches this — any mutation after handoff ... produces a hash mismatch."
- **Attack:** Verify-at-read as described is two operations: re-hash the file, then open and read it. A mutation landing between the successful re-hash and the open passes the check and is read — the check catches mutation between *handoff and re-hash*, not between *re-hash and read*. The named TOCTOU failure mode is therefore not closed by the stated mechanism, only narrowed. Separately, the five named modes cover only the artifact side: nothing covers the recorded handoff hash in the task record being absent, corrupted, or associated with the wrong task (builder crashes after writing the artifact but before recording the hash; two tasks' records swapped). A real implementation will hit "no recorded hash to compare against" on its first builder crash.
- **What would have to change:** (a) Specify that the verified bytes themselves — not a re-opened path — are what the answerer reads (hash-then-read-from-the-same-open-fd, or read-then-hash-the-bytes-in-memory), closing the residual window; (b) add failure modes for missing/corrupt/mismatched recorded hash in the task record, each with a fail-closed verdict.

**6. §2 — The builder's gold-`answer_ids` boundary is asserted, not enforceable, and the flagged gap covers a different leak.**
- **Claim:** "The builder never sees the gold `answer_ids` for the query it is building against — nothing in its inputs includes them," and per the architecture rule "every role boundary in this section is phrased as something a runner can check or refuse."
- **Attack:** The only boundary with a named mechanical enforcement is the *answerer's* (REQ-78 strip boundary, Phase 21). For the builder, "nothing in its inputs includes them" is a construction claim with no named check — and the builder *does* read the STaRK corpus, the same artifact family in which `answer_ids` live (the QA dataset and the KB ship together; `load_qa` returns rows containing `answer_ids`). Nothing in §2 or §3 states what stops the builder's data-loading path from touching the QA rows' answer fields. The gap §2 does flag — builder content-smuggling into the subgraph — is a *different* leak (output side) from the builder reading gold ids (input side), so the flagged gap does not cover this one. The claim "every role boundary ... is phrased as something a runner can check" is not true of this boundary as written.
- **What would have to change:** State the mechanical input-side constraint for the builder (e.g., the builder's loader receives a KB-only view with the QA answer fields stripped, named as a Phase 20/21 requirement with a requirement id), or explicitly add "builder reads gold `answer_ids` via the shared dataset" to the flagged-gaps list alongside content-smuggling.

**7. §4 — The decision statement counts licence as a ground for PrimeKG while the PrimeKG dataset licence is unverified.**
- **Claim:** "PrimeKG is selected over Amazon and MAG on ... an independently-retrieved cc-by-4.0 dataset licence with the PrimeKG codebase/dataset licence distinction stated explicitly (licence)."
- **Attack:** The cc-by-4.0 licence is STaRK's dataset licence — it attaches identically to all three candidate KBs (Amazon, MAG, Prime) and therefore cannot discriminate among them. The licence that *would* discriminate — PrimeKG's own dataset licence — is stated in the same section to be unverified. As written, the decision statement presents "licence" as one of three grounds favoring PrimeKG when the verified evidence is (a) non-discriminating (STaRK cc-by-4.0) and (b) affirmatively unknown (PrimeKG dataset licence). The body text is careful; the decision statement is not.
- **What would have to change:** Reword the decision statement so the licence ground reads as "STaRK's cc-by-4.0 verified; PrimeKG dataset licence unverified and recorded as an open item (§10)" — i.e., licence is neutral-to-unresolved, not a ground of selection — or drop licence from the three grounds and rest the decision on size and replay.

**8. §1/§9 — The "pinned mechanically" freeze claim is stronger than what §9 delivers.**
- **Claim (§1):** Ancestry "is pinned mechanically by a committed freeze test ... rather than relying on a reviewer's memory." Claim (§9): "Directory placement within `src/foundry/` is Phase 20's and Phase 21's to settle — this section pins the top-level filenames only."
- **Attack:** A path-watching ancestry guard cannot watch a path whose directory component does not yet exist and is explicitly unsettled. Until Phase 20 chooses a directory, the guard either watches nothing (vacuous pass) or watches a guessed path that may never exist (vacuous pass again) — in both cases the "mechanically pinned" property §1 advertises does not hold during exactly the window (first implementation commits) it exists to cover. A freeze test that passes vacuously is worse than none because it manufactures the appearance of enforcement.
- **What would have to change:** Either pin full relative paths in §9 (the design's job, per its own "the guard can only watch paths this document names"), or state in §1 that the guard is inert until the Phase 20 directory decision lands and name the mechanism that activates it (e.g., the freeze test fails until the watched paths exist).
