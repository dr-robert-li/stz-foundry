## Reviewer: oc-gpt-sol-pro

**Verdict: UNSOUND**

## 1. Critical Defects

1. **Stage 2 cannot apply the “same acceptance rule.”** Section 4 requires arm-order consistency across ≥5 of 6 seeds, but Stage 2 has only 3 seeds. This is mathematically impossible or invites an undocumented reinterpretation.  
   **Fix:** Specify a Stage-2 rule, such as consistent signs on all 3 seeds, or define the consistency test over the combined 9 Stage-1/Stage-2 seeds. The latter is not an independent re-qualification, so all 3 fresh seeds is cleaner.

2. **The noise-based selection rule creates selection bias.** Selecting the qualifying point with the smallest noise from one draw and two replicates preferentially selects a downward noise estimate. The subsequent headroom test uses that same selected estimate, making it anti-conservative.  
   **Fix:** Use a predeclared point priority independent of measured noise, or estimate noise on independent draws after selection. At minimum, select using a conservative upper confidence bound from enough replicates.

3. **The format-stability gate has no failure disposition.** It “runs FIRST” and has requirements, but the document does not say whether any failure terminates v3.1, excludes a point, or permits the difficulty probe.  
   **Fix:** Precommit the exact consequence and whether requirements apply per point × seed cell or pooled across observations.

## 2. Acceptance Rule

- Clause 1 does not specify the CI method, estimand, or treatment of 10 tasks nested within each seed. Two implementers could use Wald, bootstrap, t, or seed-clustered intervals and reach different decisions. Define the CI algorithm, including bounds and rounding.
- `n=60` is not adequately justified for this endpoint. Phase A variance includes strict-parser structural zeros, while v3.1 deliberately changes that distribution. “Width” is also ambiguous between total width and margin of error.
- Stage 2 uses only `n=30` while demanding the same corridor-containment test, with no power or precision justification. This can turn re-qualification into another winner’s-curse lottery.
- Clause 3 must define `exact`: binary exact-match rate, exact-score mean, or an existing named metric.
- Clause 4 constrains no-artifact only in the baseline arm. A fence-dominated s0 arm could still qualify and manufacture separation. Apply the budget to both arms.
- Clause 5 must define per-seed aggregation and the handling of ties.
- The ceiling probe’s “score ≥0.95 everywhere” needs an explicit denominator and aggregation rule.

## 3. One-Shot Termination

“No v3.2” is label-based and therefore gameable. A materially equivalent successor could be called v4, another arm, or a new instrument line. “Diagnostic” fresh draws could also become design evidence.

**Fix:** Prohibit any successor preserving this hypothesis, task family, and arm comparison while changing parser, prompts, grid, scoring, or qualification rules, regardless of name; state whether diagnostics may support future instrument design.

## 4. Falsification

“Differs strongly” is unmeasurable and has no binding consequence. Predefine the between-arm gap threshold, uncertainty calculation, and whether exceeding it disqualifies the point. Also precommit outcomes for G1, ceiling-gate failure, large overall strict/relaxed divergence, and alias extraction from multiple `json` blocks.

## 5. Further Underspecification

Define multiple-alias-block behavior, malformed explicit-block behavior, parser error classification, task independence, randomization/order, model sampling parameters, retry policy, missing-task handling, checkpoint resumption, and whether reused Stage-1 seeds regenerate identical warehouses.

## Reviewer: oc-qwen-max

"the strict-endpoint gap differs strongly BETWEEN ARMS" — no threshold. An implementer can't flag this automatically, and a reviewer can't audit it post-hoc.

## Reviewer: ollama-gemma4

**Verdict: SOUND-WITH-CHANGES**

### 1. Critical Defects
**Acceptance Rule §4, Clause 3 ($\text{mean(graded)} - \text{mean(exact)} \ge 0.10$):**  
This clause requires the relaxation to provide a minimum $10\%$ performance boost for a point to qualify. While this proves that the "nuisance" existed and was mitigated, it creates a **selection bias against "already healthy" points**. If a specific prompt/task is naturally well-behaved (low dialect drift), it will be disqualified here despite being potentially ideal for the corridor. 
*   **Fix:** Change Clause 3 to: `(mean(graded) − mean(exact) ≥ 0.10) OR (relaxed no-artifact rate ≤ 0.05 on baseline)`. This allows points that are either "rescued" by relaxation or were never broken to begin with.

### 2. Acceptance Rule (§4)
*   **Measurability:** All clauses are measurable via the checkpoint state described in §3.
*   **Gameability:** The rule is robust. Since it's a pre-registration and seeds/tasks are fixed, there is no room to "cherry-pick" seeds after seeing results. 
*   **Sample Size ($n=60$):** Justification is sound. Moving from $n=10$ (CI $\sim 0.25$) to $n=60$ targeting CI $\le 0.20$ follows standard power scaling for the observed variance in Phase A. The use of fresh seeds (11, 101, 2027) ensures this isn't just a re-run of old luck.

### 3. One-Shot Termination (§5)
The termination rule is airtight. By explicitly stating that failure to pass Stage 1 + Stage 2 ends the **entire v3 instrument line** (including prohibitions on new grids or v3.2), it prevents iterative "tweaking" until a point passes. The only path forward is a terminal report admitting the instrument failed to resolve format confounds. No loopholes detected.

### 4. Falsification (§7)
The falsification section is comprehensive. Specifically, recording **asymmetric benefit** (if $\text{relaxed} - \text{strict}$ differs between arms) prevents the operator from ignoring a case where the "strong" arm is simply better at following strict formatting than the "minimal" arm, which would make the relaxation a hidden proxy for capability.

### 5. Specification / Implementer Divergence
The document is highly specified:
*   **Parsing Grammar:** The info string `json` (exact match) and the priority logic (Explicit $\rightarrow$ Alias $\rightarrow$ Fail) are unambiguous.
*   **Instrumentation:** Requirements for raw text, dual flags, and tokens provide a clear blueprint for the data store.
*   **Pipeline:** The format-stability baseline acting as a "gate" before the difficulty probe ensures that failure is attributed to difficulty, not a systemic model inability to produce fences at length.

**Two implementers would build identical instruments.**

### 3. One‑Shot Termination Rule (§5)

The rule “If NO point passes stage 1 + 2 under these rules, v3 terminates” is unambiguous and prevents any post‑hoc mitigation (v3.2) because no new grid or arm can be introduced afterward. A remaining loophole could arise if a user mis‑interprets that **stage 2 still uses fresh seeds**; to close this, explicitly add “Stage 2 employs *only* the three designated fresh seeds and no additional mitigating changes.” The existing text already says this, but reinforcing it with an explicit prohibition on seed swaps would eliminate any ambiguity.
